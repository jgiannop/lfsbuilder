# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

lfsbuilder is a **Linux distribution builder on Gentoo**: a recipe file says what the system is (init system, CPU level, compiler flags, USE flags, packages, language, network, output), and the build turns it into a system, in Docker, reproducibly. Later a Qt form with checkboxes writes the recipe, and the output becomes the owner's own distribution (ISO, installer, branding, a binary package server for updates). Repository: https://github.com/jgiannop/lfsbuilder (branch `master`). The name stays for now (owner's decision).

The project started on Linux From Scratch; that work (the LFS book read from its XML, the sources fetched, chapters 4–8 run in Docker) is on the branch `lfs`, kept for reference.

## Decisions taken (with the owner)

- **Gentoo, not LFS, as the base** (2026-11-17): Portage gives dependency resolution, updates and binary packages; USE flags are the form's checkboxes; Gentoo's official binary packages make builds fast; user patches (`/etc/portage/patches`) are where the agent's fixes go. The price: the start is Gentoo's prebuilt stage3, and the result is a Gentoo derivative (rebranded, per Gentoo's name and logo guidelines).
- **Everything pinned and checked**: the recipe names a stage3 build (date) and a commit of `github.com/gentoo-mirror/gentoo` (the repository with its metadata cache, every commit signed). The stage3 must be signed by Release Engineering's automated key `13EBBDBEDE7A12775DFDB1BABB572E0E2D182910`, the commit by the repository mirror key `EF9538C9E8E64311A52CDEDFA13D0EF1914E7A72`; the fingerprints are in `gentoo.py` and decide (the key file from qa-reports.gentoo.org is only where the keys come from). Gentoo deletes old stage3s after some months: the copies in `work/gentoo/` keep old recipes buildable (later: an archive the owner chooses).
- **systemd by default** (GNOME needs it); `openrc` is a recipe option (tested: `recipes/openrc.toml`).
- **Gentoo's binary packages on by default**, required to be signed (`verify-signature = true` in `binrepos.conf`; not `FEATURES=binpkg-request-signature`, which also rejects our own unsigned packages). A package is compiled when its USE flags differ. Custom `cflags` don't stop binary packages being used: for compiler flags to apply everywhere, `binary_packages = false`.
- **Docker as the build host, without `--privileged`**: a `--privileged` container is not a security boundary, and an agent running commands it chose must be sandboxed. Portage's namespace sandboxes are off (they need unshare); its LD_PRELOAD sandbox stays.
- **Checkpoints after every step** as Docker images named by a fingerprint (hash chain of the stage3's SHA512, the repository commit and every step's script); each package of the recipe is its own step. Portage's binary packages (`buildpkg`) in a volume per CPU level and flags are the package-level cache.
- **The agent repairs, the recipe stays the truth**: Claude is only called when a step fails or a decision is needed, with the failing command and the end of the log, never whole logs (gigabytes); its fixes are stored with the recipe (USE changes, `package.accept_keywords`, user patches) so the next build is reproducible without it.
- **Making it bootable**: QEMU with the kernel and initramfs given directly; the disk image is made by `mke2fs -d` from a tar (no loop devices, no root). Real disks get GPT partitions and GRUB from the installer on the live ISO (phase 3). A running VirtualBox VM holds VT-x on the owner's i7-3770, and KVM guests then die with `KVM: entry failed, hardware error 0x0`; `boot_test()` sees that and boots again without KVM (slower).

   - **`check RECIPE`** (`lfsbuilder/check.py`, done): `emerge --pretend` in a container of the `portage` checkpoint, looping: take the first `- pkg (Change USE: +x)`, add it to a scratch package.use, ask again; report the USE changes the recipe needs (to paste into `[use.packages]`) and how many packages are binary vs compiled (exit 1 if changes are needed). 2. **The agent** (first version 2026-11-17, `build --repair`): on a failed step, `repair.diagnose()` sends dependency problems ("Change USE" etc.) to `check` (no Claude), anything else to Claude through Claude Code (owner's choice: `claude -p --tools "" --strict-mcp-config --no-session-persistence --output-format json --json-schema SCHEMA --system-prompt SYSTEM`, run in an empty temp dir so this CLAUDE.md isn't loaded; the answer is in `structured_output`). Claude gets the step's script, the failing command, the last 60 lines of the step log, the last 150 of Portage's build.log (copied out of the failed container by the runner as `<step>.portage.log`), the recipe with password hashes hidden, and the fixes already tried. Fixes (kinds: use, keywords `~amd64` only, env, patch) are checked by `Fix.problems()` and saved in `<recipe>.fixes.toml` (patches in `<recipe>.patches/`), applied at the start of their step; up to 3 attempts, and a fix already tried isn't tried again. Tested: a testing-only package (app-misc/abduco) → Claude proposed `keywords ~amd64` ($0.03), the retry built. Later: the API as a second way to call Claude; the form's Build with repair.

## Layout

- `lfsbuilder/recipe.py`: loads and checks a recipe (TOML, `tomllib`). Everything that ends up in a shell script or `make.conf` is checked against a pattern first. Passwords are only ever crypt hashes (`$6$`, `$y$`, ...), made by `python3 -m lfsbuilder password` (openssl in the tools image, the password on stdin); recipes go into git. The example's `demo` user has the hash of "demo", for QEMU only.
- `lfsbuilder/gentoo.py`: `keyring()`, `stage3()` (download, verify `.asc`), `repository()` (git fetch of one commit, `verify-commit`, `git archive` to a plain tree), `stage3_image()` (`docker import` of the stage3). gpg and git run in the tools image (`docker/host.Dockerfile`, `lfsbuilder-host:dev`).
- `lfsbuilder/steps.py`: the steps as shell scripts written from the recipe, least-changing first (so adding a package doesn't redo the kernel): `portage` (make.conf, package.use, binrepos.conf, dracut config, profile), `world`, `kernel` (`gentoo-kernel-bin` with `installkernel[dracut]`), `system` (time zone, locale, keymap, network, services), one per package (plus `net-misc/networkmanager` if chosen, `app-admin/sudo` if `users.sudo`), `services` (`systemctl enable` / `rc-update add`, after the packages), `users` (accounts; hashes set under `set +x` so they stay out of logs; locked when empty). /etc/hostname, hosts, resolv.conf are Docker's in a container: they are written at export.
- `lfsbuilder/runner.py`: runs steps (`run()` returns the failed `Planned` or None) (container `lfsbuilder-step-<fingerprint>`, so builds of different recipes can run at once) (`bash -l`, `set -x` with `PS4='### lfsbuilder: '` so the log shows the failing command; the script goes in on stdin and runs as `/dev/fd/3` with stdin `/dev/null`: as one argument it hit Linux's 128 KB limit with the branding step's pictures, and `eval` would double PS4's first `#`), commits each as `lfsbuilder-build:<fingerprint>`, skips steps whose image exists, flattens images over 100 layers. Mounts: the repository read-only at /var/db/repos/gentoo, volumes `lfsbuilder-distfiles` and `lfsbuilder-binpkgs-<cpu>-<hash of flags>`. `MAKEOPTS` from `jobs` is passed in the environment (not fingerprinted).
- `lfsbuilder/image.py`: `export()` (docker export → `rootfs.tar`, Docker's files replaced from the recipe, fstab added, kernel/initramfs copied out), `disk()` (`mke2fs -d rootfs.tar`), `boot_test()` (QEMU with 4 GB, a virtio graphics card and no window, the monitor on a unix socket; waits for `login:` on the serial console, then `settle` seconds, then `screendump` → `screen.png` via a stdlib PPM→PNG converter; Claude can look at the PNG).
- `lfsbuilder/__main__.py`: `python3 -m lfsbuilder prepare|plan|check|build|boot RECIPE` (`build --until <step name>`, `boot --console` to log in on the serial console, Ctrl-A X quits), `python3 -m lfsbuilder password`, `python3 -m lfsbuilder clean [--yes]` (removes `lfsbuilder-build` images no recipe in `recipes/` plans now; lists only without `--yes`; never run with `--yes` without the owner's word). `boot` deletes `rootfs.tar` after making `disk.img`; `iso RECIPE` makes `work/build-<recipe>/<recipe>.iso` and boot-tests it (BIOS, and UEFI when OVMF is installed). Work files in `work/` (ignored by git): `gentoo/{keys,stage3,repos}`, `build-<recipe>/{logs,boot,rootfs.tar,disk.img}`.
- `lfsbuilder/fixes.py`: `Fix`, `load()`/`save()` of `<recipe>.fixes.toml`, `script()` (writes package.use / package.accept_keywords / env + package.env / patches files); `recipe.load()` attaches them as `recipe.fixes`, `steps.all_steps()` puts each at the start of its step (a fix naming a step the recipe lacks is an error).
- `lfsbuilder/repair.py`: `diagnose()`, `ask_claude()`, `prompt()`, `SYSTEM`, `SCHEMA` (above, phase 2).
- `lfsbuilder/presets.py`: the form's choices: desktops (profile, packages, services, network manager, the USE changes `check` found; offered only when `tested`), software checkboxes, common locales/zones/keymaps.
- `lfsbuilder/form.py`: the Qt form (PySide6). Holds no state of its own: `load()` fills the widgets from a recipe, `recipe()` makes one from them (`dataclasses.replace` on the loaded recipe, so unshown fields stay), save is `recipe.dump()` then `recipe.load()` for the checks. Packages are ordered desktop, software (in `SOFTWARE` order), others; `steps.package_use()` sorts its lines so the order USE changes were written in never changes a fingerprint. Run: `.venv/bin/python -m lfsbuilder.form [RECIPE]`. The venv: `python3 -m venv --without-pip .venv && python3 -m pip --python .venv/bin/python install PySide6-Essentials` (the system lacks python3-venv's ensurepip; the user's ~/.local pip does the install). Test without a screen: `QT_QPA_PLATFORM=offscreen`, `window.grab().save(...)` to look at it.
- `lfsbuilder/overlay.py`: the argo repository (profile, argo-release, argo-meta) written from the recipe (above, phase 3).
- `lfsbuilder/calamares.py`: the graphical installer's configuration and branding (above, phase 3).
- `lfsbuilder/estimate.py`: step times recorded and build estimates (above, phase 4).
- `lfsbuilder/binhost.py`: `signing_key()`, `fingerprint()` (gpg in the tools image, the key on stdin), `publish()` (in a `--network none` container of the recipe's portage checkpoint), `publish_repository()`, `serve()` (no directory listings; `/gentoo.git/` through git http-backend as CGI). `lfsbuilder/trust.sh` → `/usr/sbin/lfsbuilder-trust`. Commands: `python3 -m lfsbuilder signing-key [--name]`, `publish RECIPE`, `serve [--bind] [--port]`.
- `recipe.dump()`: a recipe as TOML (load → dump → load gives the same recipe; comments are not kept).
- `recipes/example.toml` (small, systemd), `recipes/gnome.toml` (desktop), `recipes/openrc.toml` (OpenRC, static address).

## Tests

`python3 -m unittest discover -s tests` (stdlib only; no Docker, no network): recipes load and round-trip; passwords and anything reaching a script are refused; bad fixes (`**` keywords, `$(...)` in env, path traversal and non-diffs in patches) are refused; a fix changes only its own step; fingerprints ignore `jobs` and change only from a change on; Portage's answers are parsed; Claude's prompt has no password hashes; PPM→PNG; `[updates]` server URL and key path are checked; the `updates` step is last, changes no other fingerprint and carries the trust helper and key whole. Run them before every commit.

## Known slow spots

- Installing binary packages: the runner passes `EMERGE_DEFAULT_OPTS` with `--jobs=<half the processors, at least 2> --load-average=<processors>` in the environment (since ca2b3be; not fingerprinted), and GNOME's 318-package step took ~21 min (was over an hour). Its log shows mostly one job running: Portage fetches in parallel but merges one package at a time. `FEATURES=parallel-install` (finer locks while merging) might help; it changes make.conf, so every fingerprint, and the gain is unmeasured: try it with the next deliberate rebuild of everything.

## How to work here

- **Ask the owner before every commit.** Never add Claude attribution or co-author lines to commits or PRs. Commits use the owner's GitHub noreply address (already the git config); the owner's real email address is private.
- Installing packages on the host (`sudo apt install …`) is the owner's to run; suggest the command.
- Builds can take long (hours without binary packages, a desktop more): say so before starting one, and run it in the background.
- The owner prefers plain-text questions and direct action.
- **Don't edit what makes a recipe's steps (`steps.py`, `installer.sh`, `fixes.py`, presets that recipes use, the recipes) while a build of it runs**: `build` plans the steps when it starts, and `boot`/`iso` after it plan again, see a changed step as not done, and refuse. A stopped `build` leaves its `docker run` going: remove `lfsbuilder-step-*` containers it left.
